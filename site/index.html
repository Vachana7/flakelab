Your pipeline just changed. What can it do now?

PipeDelta reads every change to your GitHub Actions workflows, by pull request or by direct push, and tells you in plain sentences which new powers the pipeline gained. Dangerous gains fail the check, with a fix for each.

The biggest 2026 attacks never opened a pull request.

GhostAction's return hit more than 30,000 repositories and wfx-loot about 8,000. Both used stolen tokens to push secret-stealing workflows straight to the default branch, so pull-request checks never ran. Where a reviewer did see a change, it was ten plausible lines of YAML. Scanners judge whether a file is weak today. PipeDelta asks a different question: what did this change add?

Diff the powers, not the lines.

A secret on its own is normal. A new address on its own is normal. The same job gaining both is how secrets get stolen, and only a before-and-after comparison sees it.

step 1

Read both versions

Workflow files and the actions stored in the repository, at the base and the head of a pull request or a push. The trust list comes from the base, so a change cannot trust itself.

step 2

List the powers gained

Secrets, addresses, token permissions, OIDC identity, triggers, outside code, caches, hidden commands, self-modification. Renames and version bumps are not counted as new.

step 3

Explain and block

One sentence per power, a concrete fix, and a failing check at the level you choose. The same report goes to the PR comment, the run summary and GitHub's Security tab.

Built like the tools it protects.

Push review new

Runs on push as well as pull requests, and fails closed if it cannot read the commit before a force push.

Plain language

"The same job can read secrets, so they could be sent there." Every finding is a sentence a reviewer can act on, with the fix next to it.

Security tab SARIF

Findings land in GitHub code scanning beside CodeQL, so they show in the PR diff and the alert list.

Second opinion

--zizmor on keeps only zizmor's new findings, explains them the same way and marks where both tools agree.

Trust list

Name the actions and hosts you rely on in .pipedelta.yml. Widening the list is itself reported.

Signed releases

Multi-arch images on GHCR, signed with Sigstore, with SLSA build provenance and an SPDX SBOM.

Add it in one file.

Mark the check as required in your branch rules so a high finding really blocks.

.github/workflows/pipedelta.yml
on:
  pull_request:
    paths: [".github/**", "**/action.yml"]
  push:                # catch direct pushes too
    branches: [main]
permissions:
  contents: read
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262
        with: { fetch-depth: 0, persist-credentials: false }
      - uses: Vachana7/pipedelta@<release commit>  # v0.5.0
        with:
          token: ${{ github.token }}
          fail-on: high
Try it locally
pip install -e .
python -m pipedelta git main HEAD
Offline demo, Docker only
docker compose run --rm ghost
